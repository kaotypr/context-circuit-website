## Run an explicit diagnostic

```sh
sh .context-circuit/cli check
```

The diagnostic examines structured workspace records, local bindings, links, IDs, dependency cycles, worktree associations, and owned knowledge. It reports an `issue` and a `resolve` for each finding.

## Read the resolution

A resolution names a command when one exists, an edit when that discharges it, or begins “needs a person” when judgment is required. Do not invent a repair command for the last category.

`check` also reports what earlier releases could not:

- A number reserved in more than one member's ID file, or twice in one, a record whose ID no file reserves, and a file in `.context-circuit/ids/` not named after a member.
- A `members.yaml` holding conflict markers or a member listed twice, two members on one band, a member ID that is a Windows device name, and roles in a schema 2 roster — each needing a person.
- Record folders that break the layout: a `reserved folder name`, a `folder named like a record holds records`, a `record file outside the folders records are read from`, and a `legacy archive folder awaits its rename to _archive/`.
- An empty plan folder left by an interrupted deletion, and a worktree prepared for a deleted plan or for an earlier plan with the same number.

## Prune versus repair

When Git no longer lists a worktree a plan is associated with, `check` recommends `worktree prune`, which drops the stale association. It keeps the `worktree repair` advice for a checkout that only moved, because repair works only on a path Git still lists.

A knowledge reviewed date is compared with commits under its code anchors. Unchanged code is not stale merely because a note is old. An optional `knowledge_review_days` threshold additionally reports old unanchored notes.

## Keep diagnostics separate from checks

`check` is not an implementation gate, consent, or independent code review. Tests, lint, builds, and observed user flows provide different evidence. Report the commands you actually ran and their results.
