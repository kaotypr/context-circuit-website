## Invocation

Run every command through the workspace's launcher: `sh .context-circuit/cli COMMAND …` from the workspace root, `sh <root>/.context-circuit/cli COMMAND …` from anywhere else, or `powershell -NoProfile -ExecutionPolicy Bypass -File <root>/.context-circuit/cli.ps1 COMMAND …` in Windows PowerShell or cmd. The launcher runs exactly the pinned version and passes the workspace root. The global flags `--workspace PATH` and `--json` may precede the command or follow the full command, but not sit between a group and its subcommand:

```sh
sh .context-circuit/cli --json status
sh .context-circuit/cli status --json
sh .context-circuit/cli help
sh .context-circuit/cli help record
sh .context-circuit/cli worktree prepare --help
```

| Command | Operations and purpose |
| --- | --- |

| `workspace` | `connect`, `base`, `remote` for the records repository. |
| `repo` | `connect`, `clone`, `init`, `base`, `remote`, `relate`, `inspect`, `fetch`. |
| `knowledge` | `clone`, `connect`, `sync`, `remote`, `list` for borrowed knowledge. |
| `context find` | Search by `--query` or get reconciliation candidates with `--repo`. |
| `record` | `create`, `approve`, `show`, `list`, `dependencies`, `complete`, `archive`, `order`, `delete`. |
| `worktree` | `prepare`, `list`, `inspect`, `move`, `repair`, `remove`, `prune`. |
| `agent` | `settings`, `configure`, `setup`, `dispatch`. |
| `extension` | `list`, `add`, `update`, `remove`, `enable`, `disable`, `sync`, `hooks`, and `allow` and `override` on request, for the extensions in `extensions.yaml`. |
| `template export` | Write the exact blank embedded seed to a new directory. |

## Read-only examples

```sh
sh .context-circuit/cli member list
sh .context-circuit/cli member presets
sh .context-circuit/cli repo inspect --id api
sh .context-circuit/cli context find --query billing
sh .context-circuit/cli record list
sh .context-circuit/cli record list --all --archived
sh .context-circuit/cli record show --id p0001
sh .context-circuit/cli record order --intent i001 --mode waves
sh .context-circuit/cli record order --plan p0001 --mode waves
sh .context-circuit/cli worktree list --repo api
```

In a workspace that lists extensions:

```sh
sh .context-circuit/cli extension list
sh .context-circuit/cli extension hooks --stage implement --when before --plan p0001 --repo api
sh .context-circuit/cli extension add --id parity --path extensions/parity --repo api
sh .context-circuit/cli extension sync
```

`extension hooks` resolves one hook point for a stage the agent fires (intent, plan, implement, review, deliver), runs the scripts allowed there, and returns an `extensions` list: the instruction files to follow, the scripts that ran under `ran`, each `each-time` script waiting for the person under `confirmation_required`, every extension skipped and why, and `stopped`, which goes to the person. `record approve`, `worktree prepare`, `record complete`, and `record archive` return the same list for their own stage and run its scripts themselves, and `hooks` refuses their `after` point. A `before` script that stops one of those commands leaves it unrun, exiting 1. Commands that change `extensions.yaml` happen only on request and return no `commit_recommended`. See [Extensions](/docs/template/extensions).

Scripts, on the person's request or answer:

```sh
sh .context-circuit/cli extension allow --id parity
sh .context-circuit/cli extension hooks --stage deliver --when after --plan p0001 --repo api --confirm clickup-sync
```

`extension allow --id ID` shows the extension's source, version, and each script hook with its command, `on_failure`, consent, and action, and allows that exact version to run for the active member on this machine. It runs nothing and writes only the ignored `.context-circuit/local/extension-trust.yaml`. The version is the commit of a remote source, or a hash of a folder source's files, and any change asks again. It is run only at the person's request; no flag skips it.

`extension hooks … --confirm ID` runs one `each-time` script listed under `confirmation_required`, passing it `confirmed: true`. It is run only on the person's yes to the action that entry names. A `standing` script needs no confirmation: allowing its version authorizes the one action its manifest names for that hook, and nothing else.

### Roles, overrides, and status

```sh
sh .context-circuit/cli extension override --id parity --allow repair-loop --rounds 2
sh .context-circuit/cli extension override --id parity --revoke repair-loop
sh .context-circuit/cli --json agent dispatch --host HOST --role x-parity-parity-verifier --plan p0001 --override repair-loop --round 1 --path WORKTREE
```

`extension override --id ID --allow NAME` allows one of four defaults the extension's manifest declares (`repair-loop`, `verify-during-execution`, `risk-review`, `delegation`), only on the person's request, and `--revoke NAME` takes it back. `--rounds N` can lower a repair loop's limit and never raise it. The command refuses a default the manifest does not declare or one outside the four, and the allowance is written to `extensions.yaml`. See [Overriding a default](/docs/template/extensions#overriding-a-default).

`agent dispatch --role x-<extension>-<role>` briefs an extension role like a shipped one, with limits no instruction lifts, and its result carries a `report` line for the role's `returns` headings. `--override NAME`, with `--round N` where the override has rounds, dispatches the verifier, fixing worker, or reviewer an allowed override needs, and is refused for any other use. A dispatch also reports `definition_path`, `definition_installed`, and `setup_required` when the role's native file is absent on this host. `agent setup` writes extension roles and skills beside the shipped ones, and its result lists the files `written`, `removed`, and `kept`.

`status` adds the worktrees this machine prepared under each open plan in `my_work`, each with its `repository`, `path`, and `branch`. For extensions it adds each allowed override and whether it is on for you, `extension_skills`, `named_stages`, and `setup_required` after an extension change. `extension list` names each extension's skills and stages. See [Roles](/docs/template/extensions#roles) and [Skills and named stages](/docs/template/extensions#skills-and-named-stages).

Replace IDs with those in your workspace. Normal output is readable YAML; `--json` provides structured values. Errors are on stderr and return nonzero status; a flag a command does not take exits 2 with that command's signature.

## Mutation is not authorization

Approval and completion commands require the actual corresponding decision. `record approve` returns `planning_recommended`; approval, completion, and `record archive` return `commit_recommended` for the records and ID files they left uncommitted, and the CLI never stages, commits, or pushes them.

```sh
sh .context-circuit/cli member add --id alex --name Alex --band 2 --role maintainer
sh .context-circuit/cli member tone --id alex --preset colleague
sh .context-circuit/cli record archive
sh .context-circuit/cli record delete --id p1002
sh .context-circuit/cli record delete --id i101 --id p1003 --confirm
sh .context-circuit/cli worktree prune --repo api
```

`member presets` lists the four tone presets, and `member tone --preset NAME` records the chosen preset's line in `members.yaml`, the same field `--tone` fills with a line of the team's own. `--preset`, `--tone`, and `--clear` are exclusive, an unknown preset name is refused with the valid ones, and a member with no tone is written for as `colleague`. The [workspace files reference](/docs/reference/workspace-files#tone-presets) lists each preset's line.

`record delete` previews the affected records, each with its author, path, and status, and the released IDs without `--confirm`; deletion requires a request and agreement to the exact preview. `--member ID` takes one member's records, `--id ID` (repeatable) takes exactly the named records or a reservation no record holds, and `--all` takes every record only while the roster lists exactly one member. A refusal returns the preview too, with `blocked_by`, `refused`, and, for `--id`, `add_ids`, and exits 1. The CLI does not commit, deliver, execute a plan, launch a model, or infer human consent. The pinned command source below contains the complete signatures and refusal behavior.
